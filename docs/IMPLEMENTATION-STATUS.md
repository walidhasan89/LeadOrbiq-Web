# LeadOrbiq Website — Implementation Status

This document tracks what has been built, what remains a verified placeholder,
and what needs real product/business input before public launch. It follows
the checklist structure in `09-VERIFICATION-AND-LAUNCH-CHECKLIST.md`.

## Summary

The repository was empty (no commits, no prior code) when this build started.
A complete Astro + TypeScript + Tailwind CSS v4 marketing site was built from
scratch per `00-CLAUDE-CODE-MASTER-PROMPT.md` and the supporting spec files in
this `docs/` folder.

## Stack actually used

- **Astro 7** (static output, `trailingSlash: "always"`)
- **TypeScript 6** in strict mode (`astro/tsconfigs/strict`)
- **Tailwind CSS v4** via `@tailwindcss/vite` (CSS-first `@theme` config, not
  a `tailwind.config.mjs` — this is the current recommended Tailwind v4
  integration path for Astro and keeps design tokens centralized in
  `src/styles/tokens.css` / `src/styles/global.css`, matching the spirit of
  "centralized design tokens" in `02-TECHNICAL-ARCHITECTURE.md`)
- **Astro Content Collections** (`src/content.config.ts`, glob loader) for
  the Help Center
- **@astrojs/sitemap** for XML sitemap generation
- **zod** (direct dependency) for content collection schemas — `astro:content`
  re-exports `z` but it's marked deprecated in this Astro version in favor of
  importing zod directly
- **sharp** (devDependency, one-off use) — see "Generated raster assets" below
- **prettier** + **prettier-plugin-astro** for formatting
- No React/Vue/Svelte islands were needed anywhere; no client framework is
  installed. All interactivity is plain TypeScript in `<script>` tags or
  native HTML (`<details>/<summary>` for FAQ, `<form>` for contact).
- No CMS, no server runtime — fully static output (`output: "static"`).

## Design-system decisions

- Implemented the "Intelligent Orbit" visual language from
  `04-DESIGN-SYSTEM.md`: orbit rings, location-pin/node motifs, glass panels,
  brand gradient (blue → violet → cyan), layered shadows, subtle grain.
- **Font**: Satoshi was specified but no licensed font files were supplied
  with this build. Per the design doc's own instruction ("use self-hosted
  files only when proper licensed font files are supplied"), the site uses
  the documented fallback stack (`Inter`, system UI stack) instead of
  self-hosting an unlicensed font. **`[VERIFY]`** — add licensed Satoshi
  WOFF2 files to `public/fonts/` and register `@font-face` in
  `src/styles/global.css` when available.
- Light/dark theme: two explicit states (light/dark) toggled via a button,
  with the *initial* value resolved from system preference when no explicit
  choice has been stored yet (`localStorage`). This satisfies
  "light, dark, system, persistent, no flash" without a three-way UI control,
  which kept the toggle simple per the design brief.
- Logo mark: original combination of an orbit ring + location-pin-derived
  node, built as inline SVG (`LogoMark.astro`), reused for favicon and OG
  image generation. No existing LeadOrbiq logo was found in the (empty)
  repository, so this is an original mark, not a placeholder.

## Generated raster assets

Social platforms and iOS require real raster images (SVG favicons/OG images
aren't reliably supported everywhere). `scripts/generate-images.mjs` uses
`sharp` to render the brand SVG once into:

- `public/images/og-default.png` (1200×630 social preview)
- `public/icons/apple-touch-icon.png` (180×180)
- `public/icons/icon-192.png`, `public/icons/icon-512.png` (manifest icons)
- `public/icons/favicon-32.png` (PNG favicon fallback)

This script is **not** wired into the build — it was run once and the output
committed as static assets. Re-run manually (`node scripts/generate-images.mjs`)
if the brand mark or OG copy changes.

## Functional interactions verified working

All of the following were tested with a headless-browser script (Playwright)
against the **production build** served via `astro preview`, not just the dev
server:

- All 17 routes return the correct status (200 for real pages, 404 for
  `/does-not-exist/`), no duplicate DOM `id`s on any page, no page-level JS
  errors.
- Desktop header: transparent→glass state on scroll (IntersectionObserver),
  "Product"/"Resources" dropdowns (click + Escape + click-outside),
  active-route styling.
- Mobile navigation: opens/closes reliably, focus moves into the panel,
  Tab-trap wraps at both ends, Escape closes it (document-level fallback
  listener, not just panel-scoped), route selection closes it, focus returns
  to the trigger button on close.
- Theme toggle: persists across reload, updates `data-theme` immediately.
- Section rail (homepage): scrollspy `aria-current` tracking, smooth-scroll
  with header-offset correction, URL hash updates.
- "How It Works" step switcher: click-to-swap panels, `aria-selected` state.
- FAQ accordions: native `<details>/<summary>`, keyboard-operable, work
  without JavaScript.
- Contact form: client-side validation with inline + summary errors,
  honeypot spam field, loading/success/error states, and an honest
  "not connected to a live inbox yet" state when `PUBLIC_CONTACT_ENDPOINT`
  is unset (the default) — it never pretends a message was sent.
- Help Center search: live client-side filtering across all articles.
- `prefers-reduced-motion: reduce`: animation durations collapse to ~0.
- Keyboard-only pass: skip link is the first tab stop and correctly moves
  focus to `#main-content`.

## Bugs found and fixed during QA (documented for transparency)

Automated interaction testing surfaced several real bugs, all fixed:

1. **Header "Add to Chrome" button visible on mobile.** `Button.astro` sets
   an unconditional `inline-flex` in its own base classes; passing
   `class="hidden lg:inline-flex"` from the caller raced against that and
   `hidden` sometimes lost. Fixed by wrapping conditionally-visible buttons
   in a plain `<div class="hidden lg:block">` instead of fighting a
   component's own display utility.
2. **Duplicate DOM ids** (`theme-toggle`, `map-dots`) from components
   rendered more than once per page (desktop + mobile `ThemeToggle`; `MapLeadVisual`
   used 3× on the homepage). Fixed by dropping the unnecessary hardcoded id
   on `ThemeToggle` and generating a unique SVG pattern id per
   `MapLeadVisual` instance.
3. **Mobile menu focus trap silently failed.** Focusing the first
   focusable element immediately after clearing `hidden` raced against the
   browser's own click/focus handling. Fixed with a short deferred focus call
   and a document-level Escape listener as a robustness fallback.
4. **Contact form: clearing a field's inline error on blur shrank that
   field's error `<p>`, which — because the shared error summary list above
   the fields also changed height as errors resolved — could shift the
   checkbox/submit button out from under an in-progress click.** This is a
   real layout-shift bug, not just a test artifact. Fixed by (a) separating
   per-field blur validation from the full-form/summary validation so fixing
   one field never rebuilds the shared error list, and (b) reserving fixed
   height for inline error text so it never changes box size.

## Environment variables

See `.env.example`. All are optional with safe fallbacks so the site builds
and runs without any `.env` file:

- `PUBLIC_SITE_URL` — used for canonical URLs, sitemap, structured data.
  Falls back to `https://leadorbiq.com`.
- `PUBLIC_CHROME_STORE_URL` — falls back to a generic Chrome Web Store link.
- `PUBLIC_CONTACT_ENDPOINT` — when unset, the contact form validates fully
  client-side and shows an honest "not connected yet" message instead of a
  fake success state. When set, it POSTs JSON to this URL.
- `PUBLIC_ANALYTICS_ID` — read into `siteConfig` but no analytics script is
  wired up; no analytics loads today (nothing to consent-gate yet).

## Known limitations / follow-ups

- No ESLint configured — only `astro check` (TypeScript) and Prettier. Add
  ESLint if the team wants stricter lint rules beyond type-checking.
- No automated test suite (unit/e2e) is part of this repo; QA for this build
  was done via ad hoc Playwright scripts against the production preview
  server, not a committed test suite. Consider adding Playwright as a real
  devDependency with committed specs if ongoing regression coverage is
  wanted.
- Contact form has no real backend; `PUBLIC_CONTACT_ENDPOINT` must be set to
  a real endpoint before launch, and that endpoint must do server-side
  validation (the client-side validation is a UX enhancement only, not a
  security boundary).
- FAQPage/SoftwareApplication/Organization/WebSite JSON-LD only encode facts
  already visible on the page — no ratings/review schema was added, per the
  "no fabricated aggregate ratings" rule.

## Tests actually run

- `npx astro check` (TypeScript, strict) — 0 errors on every iteration of
  this build, including the final one.
- `npx astro build` — succeeds, 17 pages generated, sitemap + robots.txt
  generated.
- `npx astro preview` — production build served and re-tested (not just dev
  server) via headless Playwright:
  - All 10 route classes (including 404) load with correct status, no
    duplicate ids, no page errors.
  - Mobile nav full interaction cycle (open, focus trap, Tab wrap, Escape,
    route-selection-closes).
  - Desktop dropdown open/Escape-close, theme toggle.
  - Contact form: empty-submit validation, full valid submission with the
    unconfigured-endpoint state, no layout-shift-induced click failures.
  - Reduced-motion animation collapse.
  - Keyboard-only: skip link is first tab stop, activates correctly.
  - "How It Works" step switcher and section-rail scrollspy.
- Browser widths tested via viewport emulation: 390×844 (mobile), 768×1100
  (tablet), 1280×900 and 1440×1000 (desktop/wide). Only Chromium was used
  for testing (Playwright's bundled browser in this environment) — Firefox
  and Safari were **not** tested; the CSS/JS used (Tailwind v4 output,
  `IntersectionObserver`, `<details>`, standard DOM APIs) has broad modern
  browser support, but cross-browser testing is still a documented gap.
- Visual review: light and dark mode screenshots of homepage, pricing, and
  use-cases pages were captured and inspected.
- **Not run**: Lighthouse (no network access to a scoring service was set up
  in this environment); actual WCAG contrast-ratio auditing tool (contrast
  was designed against the documented token values but not machine-verified
  with an automated contrast checker); screen-reader software (NVDA/VoiceOver)
  was not used — accessibility testing here was DOM/ARIA-state verification
  via Playwright, not real assistive-technology testing.
